## WO-basierter Bestandsfilter + PLH-Station + Rückwärts-Trace

### Context

**Kernproblem**: Bestandsdaten (Staging/Debox/PostBlast/Plating) haben keinen sinnvollen KW-Bezug über `DB_CHANGE_COMMIT_TIME`. Der Filter muss WO-basiert sein: "Zeige nur Items die laut Workorders dieser KW gebraucht werden."

**Snowflake-Daten bestätigen**:
- PLH-Locations (PLH-01-16, PLH-02-02, etc.) = 27 SKUs, 1.49M Einheiten (Holding vor Plating)
- PLATING-LINE-01/02/03 = 151 SKUs, 165K Einheiten (aktiv auf der Linie)
- KW35-WO Items sind über PostBlast (19M), PreBlast (2.1M), Debox (466K), PLH (78) verteilt
- Die Kette: Inbound → Staging → Debox → PreBlast → PostBlast → PLH → PLATING-LINE

### Implementation Steps

#### 1. WO-basierter SKU-Filter (`WmsKwOverviewView.tsx`)

Ersetze den `weekPlannedSkuSet` (aus DataBundle.weekRecipes) durch einen **direkt aus den geladenen WO-Daten gebauten** SKU-Filter:

```ts
// Neues woSkuSet: alle submeal/meal-Items der geladenen KW-Workorders
const woSkuSet = useMemo(() => {
  const set = new Set<string>();
  for (const r of rawWorkorders) {
    const sub = skuKey(r.submealItemNumber);
    const meal = skuKey(r.mealItemNumber);
    if (sub) set.add(sub);
    if (meal) set.add(meal);
  }
  return set;
}, [rawWorkorders]);
```

`inWeekScope` nutzt dann `woSkuSet` (wenn weekScopeFilter ON) — damit zeigen alle Bestands-Stationen nur Items die für diese KW gebraucht werden.

**Wichtig**: `rawWorkorders` muss VOR den Bestandsfiltern berechnet werden (ist bereits der Fall).

#### 2. PLH als eigene Station (`wmsTypes.ts` + Server)

- `StationKey` erweitern: `"platingHolding"` hinzufügen
- `STATION_ORDER` erweitern: `[..."postblast", "platingHolding", "plating", "sleeving"]`
- `STATION_META` erweitern: `platingHolding: { label: "Plating Holding", icon: "🧊", bgColor: "bg-indigo-50", ... }`
- **Server**: Neuer Endpoint `/wms-plating-holding` oder Plating-Query aufteilen in PLH-only vs LINE-only
  - PLH: `LOCATION_ID ILIKE 'PLH%'`
  - PLATING-LINE: `LOCATION_ID ILIKE 'PLATING-LINE%' OR LOCATION_ID ILIKE 'PLSTG%'`
- `AllData` erweitern: `platingHolding: StoredPayload`
- `WmsKwOverviewView.tsx`: separates fetch + Tab für PLH

#### 3. Rückwärts-Trace ("Zwiebel-View") — neues `WmsMealTracePanel.tsx`

Pro Meal-WO zeigen:
- **Soll** (aus WO): welche Submeal-Items, welche Menge
- **Ist pro Station**: Was liegt wo auf dem Weg zur Plating-Line
  - PLH: bereit
  - PostBlast: fertig gekühlt, muss noch in PLH
  - Debox: ausgepackt, wartet auf Blast
  - Staging: eingelagert, muss noch ausgepackt werden
- **Delta**: Was fehlt? → "Nachkochen"-Signal

Datenstruktur:
```ts
type MealTraceEntry = {
  mealSku: string;
  mealName: string;
  woNumber: string;
  submeals: {
    sku: string;
    name: string;
    required: number;
    inPlatingHolding: number;
    inPostBlast: number;
    inDebox: number;
    inStaging: number;
    inSleeving: number;
    total: number;
    gap: number; // required - total
    status: "ready" | "partial" | "missing";
  }[];
  overallReadiness: number; // 0-100%
};
```

#### 4. Filter-Toggle UX anpassen

Der `weekScopeFilter`-Button wird zu:
- **ON**: "🎯 Nur KW 35 Items" — zeigt nur Items die in KW35-WOs vorkommen
- **OFF**: "◯ Alle Bestände" — zeigt alles (aktueller Zustand)

Default: **ON** (weil jetzt WO-basiert und zuverlässig).
