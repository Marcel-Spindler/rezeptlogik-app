## Context

Drei Probleme identifiziert:

**Problem 1: Plating-Plan Parse-Fehler** — `parsePlatingPlanCsv` (Zeile 50) erwartet eine Zeile mit `"Code"` in Spalte A als Header. Die hochgeladene Datei `PET-Verden-2026-W36.csv` ist ein **PET-Plan**, kein Plating-Plan — sie hat ein anderes Format. Der Parser schmeißt korrekt den Fehler. → Entweder die richtige Datei hochladen (F_VE Production Plan – Plating Plan), oder einen eigenen PET-Plan-Parser bauen.

**Problem 2: Banner "Backfills zeigt KW 35"** — Das ist NICHT der `DataHealthBanner`, sondern der `BackfillAlertBanner`. Er zeigt an wenn `isStaleWeek = true`, d.h. `resolvedWeekNum !== currentWeekNum` (`BackfillsContext.tsx:100`). Das passiert weil der **Produktionsplan** (`data.productionPlan.rows`) keine Zeilen mit Work-Orders für die aktuelle KW 36 enthält. Der KET-Import hat damit nichts zu tun — es fehlt ein neuer Produktionsplan-Import (GSheet-Import oder `npm run import:gsheet`).

**Problem 3: Lokaler Vollimport nicht webapp-übergreifend** — `npm run import:local` schreibt nur nach `public/data/data.json` (lokal). Laut `dataSource.ts:4` wird `VITE_DATA_SOURCE` geprüft — wenn die App im Production-Modus auf Firestore läuft (`"firestore"`), nutzen andere Clients Firestore, nicht die lokale JSON. Der lokale Import aktualisiert nur den lokalen Dev-Server. Damit andere Instanzen die Daten sehen, muss nach dem lokalen Import noch `npm run push:firestore` laufen (steht auch in `package.json:41` als Teil von `sync:all`).
