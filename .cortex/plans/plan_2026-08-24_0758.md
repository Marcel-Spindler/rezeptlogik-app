## Context

**Aktuelles Problem:** Die PLH-Query (`WMS_PLATING_HOLDING_SQL`) holt nur den **aktuellen Bestandssnapshot** aus `T_STORED_ITEM` (46 Zeilen, 27 SKUs, 5 Locations). Aber in Wirklichkeit hatten **61 Locations mit 180 SKUs** in den letzten 60 Tagen Aktivität. Material fließt durch PLH hindurch (Putaway → Pallet Move → Plating Line / Lost), und der reine Ist-Bestand verpasst alles was bereits weiterbewegt wurde.

**Datenverlust-Ursache:** Die WMS-Übersicht nutzt PLH-Daten für die SKU-Bilanz und MealOperations (Submeal-Trace). Wenn ein Submeal schon aus PLH raus ist (z.B. auf Plating Line bewegt), sieht die Übersicht es nicht mehr — obwohl es verarbeitet wurde. Der durchlaufende Charakter von PLH geht verloren.

**Lösung:** Eine eigenständige PLH-Query die **beides** liefert:
1. **Aktueller Bestand** (T_STORED_ITEM, wie bisher)
2. **Bewegungshistorie** (T_TRAN_LOG) — was in der gewählten KW durch PLH geflossen ist (Putaway IN, Picks OUT, Lost, Cycle Counts)

## Implementation Steps

### 1. Neue SQL-Query im Local Server (`scripts/wms-local-server.ts`)

Neue Konstante `WMS_PLH_ENRICHED_SQL` die T_TRAN_LOG für PLH-Bewegungen der gewählten KW abfragt:
- Inbound (Tran 212): Was wurde in PLH eingelagert
- Outbound (Tran 203/204): Was wurde rausbewegt (→ Plating Line)
- Lost (023/026): Was wurde als Lost gebucht
- Cycle Count (800): Bestandskorrekturen

### 2. Neuer API-Endpoint `/wms-plh-detail`

Eigenständiger Endpoint im Local Server der:
- Den bestehenden T_STORED_ITEM Bestand holt (wie bisher, unverändert)
- Zusätzlich die T_TRAN_LOG Bewegungen der gewählten KW holt
- Beides als getrenntes Payload zurückgibt: `{ stock: StoredRow[], movements: PlhMovementRow[] }`

### 3. Neuer Typ `PlhMovementRow` und `PlhDetailPayload` in `wmsTypes.ts`

```ts
export type PlhMovementRow = {
  itemNumber: string;
  tranType: string;
  description: string;
  fromLoc: string;
  toLoc: string;
  tranQty: number | null;
  huId: string;
  lotNumber: string;
  tranDate: string | null;
  kw: number | null;
};

export type PlhDetailPayload = {
  ok: boolean;
  stock: StoredRow[];
  movements: PlhMovementRow[];
  summary: {
    totalPutaway: number;
    totalPicked: number;
    totalLost: number;
    cycleCountDelta: number;
    activeSkus: number;
    activeLocations: number;
  };
  error?: string;
};
```

### 4. Fetch-Funktion in `wmsFetch.ts`

Neue `fetchPlhDetail(week)` Funktion die den neuen Endpoint aufruft — unabhängig vom großen 9-fach-Parallelfetch, damit PLH-Daten nie im Batch untergehen.

### 5. Integration in `WmsKwOverviewView.tsx`

- Separater `useEffect` der `fetchPlhDetail` aufruft
- PLH-Tab zeigt zusätzlich die Bewegungshistorie (Eingang/Ausgang/Lost pro KW)
- MealOperations nutzt die Movements um "durchgeflossene" Submeals korrekt als verfügbar zu werten

### 6. Aggregation in `wmsAggregate.ts`

Neue `aggregatePlhMovements()` Funktion die Movements nach SKU gruppiert und pro SKU eine Bilanz erstellt (putaway, picked, lost, net).
